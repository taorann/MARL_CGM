# Current Code Evidence Map

This file records a focused audit of the current repository. Its purpose is to increase confidence in the asset documents without forcing a future implementation to preserve the old file layout.

## Audit Method

This was not generated by a full dynamic tracer. It is a static and operational-path audit:

- checked the current eval entrypoint and default launch script;
- checked the planner action contract and prompt source;
- checked the environment action handlers;
- checked sandbox and remote_swe runtime wiring;
- checked CGM HTTP client, service, graph schema, and graph-aware runtime;
- checked telemetry and progress logging surfaces;
- cross-checked these against the runbook and recent debug conclusions.

The audit intentionally ignores unrelated upstream/reference projects unless they are part of the active call path.

## Main Finding

The current implementation still uses rLLM as an execution wrapper in the eval path, but the agent design itself is train-free and can be rebuilt without rLLM.

Current eval path:

```text
scripts/run_eval_graph_planner.sh
  -> scripts/eval_graph_planner_engine.py
     -> _ensure_rllm_components()
        -> GraphPlannerRLLMAgent
        -> GraphPlannerRLLMEnv
        -> AgentExecutionEngine
     -> GraphPlannerRLLMEnv wraps PlannerEnv
     -> PlannerEnv executes the actual code-repair environment
```

Interpretation:

- rLLM currently provides the rollout loop shell, task execution engine, and adapter interfaces.
- The core agent semantics live below that shell: action protocol, PlannerEnv state machine, graph memory, sandbox runtime, CGM repair, patch validation, and telemetry.
- A clean reimplementation should replace the rLLM shell with a plain Python planner loop.

## Evidence By Asset Claim

### Train-Free Two-Model Agent

Evidence:

- `scripts/run_eval_graph_planner.sh` launches eval with planner endpoint and CGM endpoint.
- `configs/eval/graph_planner_eval_defaults.yaml` configures `planner_base_url`, `planner_model`, `planner_temperature`, and `cgm_endpoint`.
- `scripts/eval_graph_planner_engine.py` sets planner and CGM environment variables, then runs rollouts.

Reusable design:

- planner endpoint + CGM endpoint + sandbox runtime.

Do not preserve:

- rLLM `AgentExecutionEngine` as a required dependency.

### Planner Action Protocol

Evidence:

- `graph_planner/core/actions.py` defines structured actions.
- `graph_planner/agents/common/contracts.py` defines the planner system prompt, allowed parameters, parser, and validation.
- The legacy prompt explicitly defined `run_failed_test`, `explore_find`, `explore_expand`, `read`, `memory_commit`, `memory_delete`, `memory_commit_note`, `repair`, and `submit`; the clean rebuild should drop planner-side `submit` and end automatically after verified repair.

Reusable design:

- one planner action per step;
- implementation-only search/read policy;
- memory-before-repair gate;
- repair feedback as hypothesis revision.

Do not preserve:

- exact prompt wording if a better prompt is developed.

### Environment State Machine

Evidence:

- `graph_planner/env/planner_env.py` owns `PlannerEnv`.
- It dispatches actions through `_handle_explore`, `_handle_read`, `_handle_run_failed_test`, `_handle_memory`, `_handle_repair`, and legacy `_handle_submit`; the rebuild keeps the dispatch split but does not need `_handle_submit`.
- It tracks W/M state, fail-to-pass evidence, no-progress counters, last repair feedback, and telemetry.

Reusable design:

- environment stepper dispatching action handlers;
- W/M/T separation;
- repair guards and rollback-aware feedback.

Do not preserve:

- the monolithic `planner_env.py` structure. Split it as described in `03_module_blueprint.md`.

### Graph Memory And Retrieval

Evidence:

- `graph_planner/memory/*` contains candidate generation, graph adapters, subgraph store, text memory, and memory types.
- `graph_planner/tools/swe_build_graph.py` builds repository graphs and supports tree-sitter/AST-style extraction.
- `PlannerEnv` maps explore/find/expand/read results into working and memory subgraphs.

Reusable design:

- graph-level retrieval and expand;
- filesystem fallback mapped back to graph nodes;
- memory hydration with full code bodies before CGM.

Do not preserve:

- issue-specific keyword bridges as core routing logic.

### Fail-To-Pass Testing And Test-Code Guard

Evidence:

- `PlannerEnv._handle_run_failed_test` collects target failure evidence.
- `PlannerEnv._handle_repair` blocks repair until trustworthy fail-to-pass evidence exists when configured.
- `graph_planner/agents/common/contracts.py` instructs the planner not to search/read/patch benchmark test code.
- `graph_planner/agents/common/chat.py` formats fail-to-pass summaries and hides benchmark test source.

Reusable design:

- tests are behavior evidence;
- test source is not repair evidence;
- failed patch feedback is reported without redirecting into test helpers.

Do not preserve:

- any hidden rewrite that makes a test path look like an implementation path.

### CGM Context And Graph-Aware Repair

Evidence:

- `graph_planner/integrations/codefuse_cgm/context.py` converts memory graph into compact indexed CGM nodes.
- `graph_planner/integrations/codefuse_cgm/schema.py` normalizes planner graph payloads into CodeFuse-CGM-style graph schema.
- `graph_planner/integrations/codefuse_cgm/client.py` builds HTTP payloads and calls the CGM service.
- `graph_planner/integrations/codefuse_cgm/service.py` starts the graph-aware CGM service and reports `runtime_mode=graph`.
- `graph_planner/integrations/codefuse_cgm/graph_inference.py` loads the language model, CodeT5 graph encoder, adapter weights, and builds adjacency-aware graph/prompt fusion.

Reusable design:

- CGM receives issue, plan, graph, snippets, constraints, and repair feedback;
- CGM output supports normalized patch schema;
- graph-aware runtime should use node embeddings and adjacency.

Do not preserve:

- text-only graph linearization as the primary route.

### Runtime And remote_swe

Evidence:

- `graph_planner/runtime/sandbox.py` defines `SandboxRuntime` and `SandboxConfig`.
- `SandboxRuntime` supports `apptainer_queue` and `remote_swe`.
- `graph_planner/runtime/remote_swe_session.py` sends JSON commands over SSH to a remote proxy and ensures remote runners.
- `scripts/run_eval_graph_planner.sh` injects verified remote_swe defaults and SSH args.

Reusable design:

- sandbox interface with start/exec/read/apply/test/rollback/build_graph;
- remote backend as a plugin.

Do not preserve:

- platform-specific paths as hard requirements outside deployment config.

### Telemetry

Evidence:

- `graph_planner/infra/telemetry.py` writes run, episode, step, event, metrics, and markdown trace records.
- `GraphPlannerRLLMAgent.update_from_model` emits visible thinking events and strips thinking from the formal action.
- eval scripts write result JSON when `--results-path` is provided.

Reusable design:

- structured JSONL plus readable markdown trace;
- visible thinking is log-only, not model memory;
- progress summaries distinguish pass/not_pass/bug.

Do not preserve:

- rLLM trajectory object shapes.

## What The New Implementation Should Replace

Replace this current wrapper:

```text
GraphPlannerRLLMAgent + GraphPlannerRLLMEnv + AgentExecutionEngine
```

with:

```text
PlannerClient
PlannerLoop
CodeRepairEnv
ActionParser
ObservationBuilder
TraceWriter
```

The core behavior remains the same; the training-oriented shell disappears.

## Confidence Level

High confidence for the architecture-level assets:

- action set;
- W/M/T memory model;
- test-source guard;
- fail-to-pass-first repair gate;
- CGM graph-aware input;
- sandbox/rollback/test loop;
- telemetry needs;
- rLLM-free reimplementation target.

Medium confidence for exact implementation details:

- current query ranking heuristics;
- current no-progress rewrite rules;
- exact graph edge extraction quality;
- current CGM patch post-processing knobs.

Those medium-confidence details should be treated as implementation options, not mandatory design constraints.
